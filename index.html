Why systemd tools?

    
Most cron jobs graduate to systemd timers eventually — on every VPS, NAS and homelab box
    running Linux. Yet the tooling never caught up: the grammar is terse, the error messages are
    silent (a unit file that never fires doesn't complain — it just quietly does nothing), and the
    few existing references are documentation, not tools. So we built the four tools we wished
    existed: generate, edit, check, convert. The same rules engine that powers them also validates
    every commit tool output — 137 automated assertions run before
    anything ships.

Questions developers actually ask


    

      Is my code uploaded anywhere?
      
No. This site is static files. Every tool is plain JavaScript running in your tab.
      There is no backend endpoint that could receive your diff, your unit file, or your
      crontab even by accident.

    

    

      Why no AI?
      
Because the trade wasn't worth it. AI means your proprietary input travels to someone
      else's server, plus quotas and API costs. A rules engine covers the daily 80% deterministically —
      correct type, correct syntax, the actual next fire times — and shows its reasoning so you
      learn the grammar instead of renting it. If a change is too tricky for rules, you should
      probably write that message yourself anyway.

    

    

      What are the systemd tools exactly?
      
Four: a unit file generator (plain fields in, correct
      .service out), an OnCalendar editor (spec in,
      parse + next 5 fire times out), a unit file checker (paste any
      unit, get the bugs with fixes), and a cron ↔ systemd converter
      that warns where the two grammars genuinely disagree — like dom+dow OR-vs-AND, or @reboot
      having no OnCalendar equivalent.

    

    

      Does the commit tool replace commitlint or semantic-release?
      
No — it feeds them. Output follows the Conventional Commits format those tools lint
      and release from, so your pipeline keeps working.

    

    

      Where is my style profile and history stored?
      
In this browser's localStorage, on this machine. "Forget my style" and the clear-history
      link remove them permanently. Clearing site data does the same.

    

    

      How accurate is type detection?
      
Strong on the common signals: test-only changes, lockfile bumps, migrations, docs,
      CI config, new exported functions. Ambiguous mixed diffs default to fix with a
      note — override the checkbox or edit before committing. As with any generator, read it once.

    

    

      Why a website instead of Copilot or aicommits in my editor?
      
Different jobs. IDE assistants want your repo open, and many want your code on someone
      else's server. This one earns its place in three situations: squash-merging on GitHub's web
      UI where you have no terminal helpers; locked-down work machines where you can't install
      anything; and learning — every output shows why, so the format rubs off on you.
      It also never asks for access to anything, because there is nothing to access.

    

    

      Why three variants instead of one answer?
      
Because the right message is a judgment call, and a single confident answer would be a
      lie. Each variant reads a different signal in your input — the thrown error message, the
      new export, the guard clause — and the why-line under each shows its reasoning. Pick one,
      tweak it, or ignore all three. That's the honest version of help.
