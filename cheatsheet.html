Conventional Commits cheat sheet

Everything the specification expects, on one page, without the tutorial voice. The format exists so that humans — and tools like commitlint and semantic-release — can read your history mechanically.

The shape

<type>[optional scope][!]: <description> [optional body] [optional footer(s)]

Real example with everything on:

feat(auth)!: use refresh tokens for sessions Sessions now expire after 24h instead of living forever. BREAKING CHANGE: the "remember me" checkbox has been removed. Refs: #412

The 11 types

TypeUse forSemVer effect
featA new user-facing capabilityMINOR
fixA bug fixPATCH
docsDocumentation only—
styleFormatting, whitespace, semicolons — no logic change—
refactorCode change that neither adds a feature nor fixes a bug—
perfA change that improves performancePATCH
testAdding or correcting tests—
buildBuild system or external dependencies (webpack, npm, cargo)—
ciCI/CD configuration (GitHub Actions, GitLab CI, Jenkins)—
choreMaintenance that touches no src or test files—
revertReverting a previous commitvaries

Subject line rules

  • Imperative mood: "add validation", not "added validation" — as if completing the sentence "if applied, this commit will…"
  • ≤ 72 characters is the safe ceiling; ~50 is the comfortable one for git log --oneline.
  • No trailing period. The subject is a headline, not a sentence.
  • Lowercase start is convention (unless the first word is a proper noun or acronym).

Scope

Scope is free-form but should match your project's module names: feat(auth):, fix(api):, chore(deps):. Consistency matters more than the specific words — pick the top-level directories of your repo and stick to them. Teams that skip scopes entirely are also following the spec; just be consistent.

Breaking changes

Two legal ways — use either, or both:

  • Put ! before the colon: refactor!: drop Node 16 support
  • Add a footer: BREAKING CHANGE: the export "parseConfig" was removed

The footer form lets you explain what broke and how to migrate. The ! form is the quick flag. semantic-release reads both as a MAJOR bump.

Footers worth knowing

Closes #123 Refs #456, #789 Reviewed-by: Z Co-authored-by: Name <name@example.com>

Common mistakes

  • Mixing concerns: one commit should carry one type. Split the diff.
  • Past tense subjects — the number one lint failure.
  • Using feat for internal-only additions; if no user can observe it, it's usually refactor or chore.
  • Giant bodies nobody reads. If the body is over ~6 lines, the commit probably needs splitting.
