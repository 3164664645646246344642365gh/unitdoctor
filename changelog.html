How subjects become a changelog

    
    
      
  1. Grouping. Conventional types map to sections: feat →
      Features, fix → Bug Fixes, perf → Performance, docs →
      Documentation, chore/ci/build → Maintenance, and everything unrecognized lands
      in Other rather than vanishing.
    2. 
      
  2. The header. A first line that looks like a version
      (v1.4.0) becomes the release heading; without one, the draft starts with
      Unreleased.
    3. 
      
  3. Breaking changes. feat!: subjects and
      BREAKING CHANGE footers are grouped up top with a ⚠️, where upgraders look
      first.
    4. 
      
  4. Keep-a-Changelog spirit. Output is plain markdown you can paste into
      your existing file — the spec it follows is on our
      resources shelf.

Quick questions

    

      Does this replace semantic-release?
      
No — it's for the releases where you write the changelog by hand and just want the
      grouping done. semantic-release automates the whole pipeline; this drafts the document in
      thirty seconds with zero setup.

    

    

      Does my commit history get uploaded?
      
No. Plain JavaScript in your tab. There is no backend to receive it.
