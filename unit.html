What the form becomes

    
    
      
  1. The file. A [Unit] section with the description, a [Service] section with
      your command, user, restart policy and (optionally) sandboxing directives, and an [Install]
      section so systemctl enable actually works.
    2. 
      
  2. The guardrail. A relative command like node app.js is the #1
      cause of status=203/EXEC — the generator refuses it and says so, instead of
      handing you a file that fails at 2 AM.
    3. 
      
  3. The install. Three commands: copy into /etc/systemd/system/,
      daemon-reload, enable --now. The last one starts it immediately
      and at boot.
    4. 
      
  4. Sandboxing, if you asked. NoNewPrivileges, ProtectSystem=full,
      ProtectHome=read-only, PrivateTmp — the cheap four that stop a compromised app from doing
      maximum damage.

Quick questions

    

      Where do I put the generated file?
      
Save it as /etc/systemd/system/<name>.service (the header comment says
      the exact path), then run the three install commands shown under the file. Permissions should
      be 644, owner root.

    

    

      Does this replace systemd-analyze verify?
      
No — nothing in a browser can see your server's filesystem or users. This catches the
      authoring mistakes that cause most failures; run systemd-analyze verify on the
      box for the full schema check. Or paste the finished file into our unit
      checker first.

    

    

      Is my command or server name uploaded?
      
No. The file is assembled by plain JavaScript in your tab. There is no backend.
